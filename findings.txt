FINDING #1 - USABLE VRAM IS LOWER THAN DECLARED VRAM
Date: 2026-11-05 | Severity: HIGH | Status: Confirmed
================================================================================

OBSERVATION
RTX 3050 Laptop (4 GB) par asal available VRAM sirf ~3.18 GB hai, kyunke
Windows WDDM display driver ~0.8 GB pehle se reserve rakhta hai.

ERROR OBSERVED
  ValueError: Free memory on device cuda:0 (3.18/4.0 GiB) on startup is less
  than desired GPU memory utilization (0.85, 3.4 GiB).

ANALYSIS
  Declared VRAM      : 4.00 GiB
  Actually free      : 3.18 GiB
  Reserved by WDDM   : ~0.82 GiB (20.5% of total)
  Max safe util      : 3.18 / 4.00 = 0.795 -> use 0.70 for headroom

RESOLUTION
  --gpu-memory-utilization 0.70  (works)
  --gpu-memory-utilization 0.85  (crashes at startup)

IMPLICATION FOR THE LIBRARY
  Library ko "declared VRAM" par bharosa nahi karna chahiye. Usse startup se
  pehle ACTUAL FREE VRAM naapni hogi (torch.cuda.mem_get_info()), warna har
  config crash kar jayegi. Yeh direct validation hai SLO-Guard (2026) ke
  "crash-aware tuning" wale argument ki: crash ek wasted trial nahi balki
  ek observation hai jise cost model mein shamil karna chahiye.

ACTION ITEM
  profiler.py mein add karein:
      free_vram, total_vram = torch.cuda.mem_get_info()
      safe_util = (free_vram / total_vram) * 0.90

FINDING #6 - BASELINE MEASURED: MODEL IS MEMORY-BOUND (CONFIRMED)
Date: 2026-11-05 | Severity: HIGH | Status: Confirmed
================================================================================

SETUP
  Model    : Qwen2.5-0.5B-Instruct, FP16
  Server   : --gpu-memory-utilization 0.70 --max-model-len 2048
             --max-num-seqs 8
  Workload : 8 short chat prompts, max_tokens=128, temperature=0
  Cost base: $0.35/GPU-hour (assumed cloud-equivalent rate)

MEASURED CONCURRENCY SWEEP
  cfg   conc   tok/s   scale  effic   TPOT  TTFTp99   E2Ep99     $/1K
  -------------------------------------------------------------------
  c1       1     143    1.0x   100%    6.9       18      902   0.0787
  c4       4     490    3.4x    86%    7.7       29     1021   0.0230
  c8       8     891    6.2x    78%    7.9       37     1067   0.0126
  c16     16    1022    7.1x    45%    7.5     1029     1983   0.0110

ANALYSIS - THE KEY RESULT
  TPOT c1 se c16 tak taqreeban FLAT raha (6.9 -> 7.9 ms, sirf +14%)
  jabke throughput 7.1x barha (143 -> 1022 tok/s).

  Agar model compute-bound hota to batch barhne par TPOT bhi usi nisbat se
  barhta. Flat TPOT + rising throughput = MEMORY-BOUND (decode phase weight
  reads par bottleneck hai, arithmetic par nahi).

  YEH CONFIRM KARTA HAI: quantization (weights chhote karna) is model par
  sab se bara lever hoga, kyunke woh seedha memory traffic kam karta hai.

ROOFLINE CHECK (cost model ka pehla calibration point)
  Theory : 0.5B FP16 = ~0.93 GiB weights / 192 GB/s = 5.2 ms/token
  Measured: 6.9 ms/token (at concurrency 1, cleanest signal)
  CORRECTION FACTOR = 6.9 / 5.2 = 1.33

  Yeh 1.33 cost model ka pehla seekha hua parameter hai. Aage har naye
  model/GPU par yeh dobara fit hoga.

IMPLICATION FOR THE LIBRARY
  Memory-bound vs compute-bound ka faisla sirf 2 runs se ho sakta hai
  (concurrency 1 aur concurrency N par TPOT compare karo). Yeh profiler
  ka sab se sasta aur sab se qeemti test hai, aur isi se library decide
  karegi ke quantization par zor dena hai ya batching par.

ACTION ITEM
  profiler.py mein "boundedness test" add karein:
      tpot_ratio = tpot_at_high_conc / tpot_at_conc_1
      if tpot_ratio < 1.3: memory_bound = True

FINDING #7 - SATURATION CLIFF AT max-num-seqs: TTFT EXPLODES 28x
Date: 2026-11-05 | Severity: HIGH | Status: Confirmed
================================================================================

OBSERVATION
  Server --max-num-seqs 8 par chal raha tha. Client concurrency 16 bheji.

  TTFT p99 : 37 ms (c8)  ->  1029 ms (c16)   = 28x JUMP
  E2E  p99 : 1067 ms     ->  1983 ms         = 1.86x
  TPOT     : 7.9 ms      ->  7.5 ms          = NO CHANGE

ANALYSIS
  TPOT bilkul nahi badla, sirf TTFT phata. Matlab GPU slow nahi hua;
  8 extra requests QUEUE mein khadi theen aur apni baari ka intezar kar
  rahi theen. Yeh classic queueing behavior hai (Little's Law), GPU
  bottleneck nahi.

  Scaling efficiency bhi yahin girti hai:
    c8  : 78% efficient  (6.2x speedup on 8x concurrency)
    c16 : 45% efficient  (7.1x speedup on 16x concurrency)
  Yani c8 ke baad throughput ka faida khatam, sirf latency ka nuqsan.

  COST PERSPECTIVE:
    c1 -> c8  : cost 84% kam  (bara faida)
    c8 -> c16 : cost sirf 13% kam, lekin TTFT 28x kharab (bura sauda)

IMPLICATION FOR THE LIBRARY
  Yeh exactly wohi "knee of the curve" hai jo library ko dhoondni hai.
  Optimal point c8 hai, c16 nahi, halanke c16 ka cost number sab se kam
  dikhta hai. Sirf cost dekh kar faisla karne wala tuner GHALAT jawab
  dega.

  Is liye library ka objective single-metric nahi ho sakta. Usse
  cost MINIMIZE karna hai SUBJECT TO p99 latency constraint. Yeh
  BOute (MLSys 2026) ke multi-objective framing ko empirically
  support karta hai.

ACTION ITEM
  1. Client concurrency aur server max-num-seqs ko ALAG knobs rakhein;
     inka interaction hi saturation point banata hai.
  2. Cost model mein queueing term add karein, sirf service time nahi.
  3. Next experiment: max-num-seqs ko 16/32 karke dekhein ke cliff
     shift hoti hai ya GPU memory pehle khatam ho jati hai.

  trade-off hi nahi tha; c16 chunna sirf GHALAT hai.

  Wajah: kal chunk-count se tokens ginay gaye the aur ek hi pass tha.
  7% noise + galat token count mila kar ~9% ka farq bana diya, jo c8 aur
  c16 ke asal farq (1%) se bohot bara hai.

  Baseline sweep ko theek karna hoga: requests ko concurrency ke saath
  scale karein (jaise requests = 8 x concurrency).

IMPLICATION FOR THE LIBRARY
  Do configs ka farq 1% hai aur measurement noise 2% hai, to unhe "tied"
  kehna chahiye, winner declare nahi karna chahiye. Agar library 1% ke
  farq par faisla karegi to woh shor par faisla karegi, data par nahi.

ACTION ITEM
  1. Planner mein tie-breaking rule: agar cost ka farq noise floor se kam
     hai, to kam latency wali config jeetti hai.
  2. baseline sweep theek karein: requests = 8 x concurrency.
  3. Noise floor ko har sweep ke saath measure aur report karein.

FINDING #22 - THE KNEE IS AT concurrency == max-num-seqs, AND IT IS SHARP
Date: 2026-11-23 | Severity: CRITICAL | Status: Confirmed (all 9 configs clean)
================================================================================

THE COMPLETE CLEAN SWEEP (noise 0.4-1.7% throughout)

 slots  conc    tok/s  theory   % of     $/1K    p99  SLO 2s
 -------------------------------------------------------------
     8     4    531.2     500   106%   0.0212    940  PASS
     8     8   1014.6    1000   101%   0.0111    998  PASS
     8    16   1045.6    1000   105%   0.0108   1972  PASS
    16     8   1011.3    1000   101%   0.0112    996  PASS
    16    16   1870.4    2000    94%   0.0060   1050  PASS
    16    32   1940.5    2000    97%   0.0058   2112  FAIL
    32    16   1871.8    2000    94%   0.0060   1037  PASS
    32    32   3231.3    4000    81%   0.0035   1217  PASS
    32    64   3466.7    4000    87%   0.0033   2345  FAIL

RESULT 1 - A THROUGHPUT LAW THAT ACTUALLY HOLDS
  throughput = min(server_slots, client_concurrency) / step_time

  Within 6% at 8 and 16 slots. At 32 slots it falls 13-19% short, which is
  where the power cap of Finding #21 starts to bite. So the law is a ceiling,
  and the gap to it is itself a measurement of saturation.

  Note that min() is the whole story: b8_c16 and b16_c8 both land at ~1010
  tok/s, because in one case the server has too few slots and in the other
  the client sends too few requests. Neither side can be read alone.

RESULT 2 - THE KNEE, AND IT IS THE SAME EVERY TIME
  Raising client concurrency BEYOND the server's slots:

     8 slots: c8  -> c16   throughput +3.1%   p99  998 -> 1972   2.0x worse
    16 slots: c16 -> c32   throughput +3.7%   p99 1050 -> 2112   2.0x worse
    32 slots: c32 -> c64   throughput +7.3%   p99 1217 -> 2345   1.9x worse

  Three independent slot counts, and all three give the same answer: past
  the knee you buy 3-7% throughput (barely above the 1.7% noise) and pay
  with double the tail latency.

  THE RULE: set client concurrency equal to max-num-seqs. Going past it is
  never worth it on this workload.

RESULT 3 - RAISING BOTH TOGETHER IS WHERE THE MONEY IS
    b8_c8  -> b16_c16 : throughput 1.84x, cost 46% lower
    b16_c16 -> b32_c32: throughput 1.73x, cost 42% lower

  Each doubling of slots AND concurrency roughly doubles throughput and
  takes ~45% off the cost, until the power cap starts eating the gain.

THE PLANNER'S ANSWER, under a 2000 ms p99 limit
    b32_c32   $0.0035/1K   p99 1217 ms   3231 tok/s   <- the answer
    b16_c16   $0.0060/1K   p99 1050 ms   1870 tok/s
    b32_c16   $0.0060/1K   p99 1037 ms   1872 tok/s

  The cheapest config overall is b32_c64 at $0.0033, but its p99 of 2345 ms
  breaks the SLO, so it is infeasible rather than cheap. The answer is
  b32_c32: 68% cheaper than the b8_c8 baseline AND with better tail latency.

  A tuner that only minimised cost would have picked b32_c64 and quietly
  broken the latency contract for a 6% saving.

IMPLICATION FOR THE LIBRARY
  This is the clean, general rule the cost model needed:
    - throughput ceiling: min(slots, concurrency) / step_time
    - the gap to that ceiling measures saturation
    - the knee sits exactly at concurrency == slots, on every slot count
    - past the knee, cost barely improves and p99 doubles
  None of this needed 480 runs. Nine clean configs gave all of it.

  And it only emerged AFTER the contaminated data was thrown out. The same
  nine configs, measured next to an orphan server, had said 16 slots were
  2.4x worse than 8.

ACTION ITEM
  1. Encode the knee rule in planner.py: never propose concurrency above
     max-num-seqs unless the user explicitly asks for burst headroom.
  2. Use min(slots, concurrency)/step as the throughput ceiling, and fit
     only the saturation gap.
  3. Re-run this sweep at 64 slots to find where the power cap flattens it.

FINDING #23 - THE PLANNER WORKS, AND COST IS COUNTED IN WHOLE GPUs
Date: 2026-11-23 | Severity: HIGH | Status: Built and running on clean data
================================================================================

THE COST MODEL VALIDATED (22 clean runs, leave-one-out)
  TPOT   MAPE   9.0 %      correction 1.52 over roofline
  TTFT   MAPE  11.8 %      27 ms + 0.025 x full^1.09 + 0.0022 x cached
  E2E    MAPE  10.0 %

THE COST FORMULATION HAD TO CHANGE

  billed by TIME, so at a fixed offered rate that number is nearly constant
  whatever the configuration. What the configuration actually decides is how
  many GPUs the rate needs:

    capacity = max_num_seqs / (output_tokens x step_time) x saturation
    gpus     = ceil(offered_rate / capacity)

  For 30 req/s on this machine:
      8 slots -> capacity  7.9 req/s -> 4 GPUs -> $0.0130 per 1K
     16 slots -> capacity 14.6 req/s -> 3 GPUs -> $0.0097
     32 slots -> capacity 26.5 req/s -> 2 GPUs -> $0.0065
     64 slots -> capacity 47.7 req/s -> 1 GPU  -> $0.0032

  That is what makes Finding #22 worth money: more slots is not a few
  percent, it is whole machines off the bill.

SATURATION, FITTED: 8-9% OF THE CEILING LOST PER DOUBLING OF SLOTS
  achieved / (slots/step):  8 slots 101%, 16 slots 92%, 32 slots 82%
  This is the power cap of Finding #21 biting harder as the batch grows.
  Without it the planner priced 64 slots at 64 req/s instead of ~47, a 30%
  overestimate on a configuration that had never been measured.

THREE BUGS THE CLEAN DATA EXPOSED IN MY OWN WORK
  1. Memory model. KV need was computed as max_num_seqs x max_model_len,
     which refused 32 slots as needing 5438 MiB - a configuration that had
     already run on this machine repeatedly. max_model_len caps ONE request;
     it does not reserve per slot, because vLLM pages the cache. With the real
     sequence length (166 tokens) the need is 1674 MiB. The server logs
     confirmed it: vLLM allocated 139,456 cache tokens where 5,312 were used.

  2. Saturation fit. Pooling every run at a slot count mixed two knee runs
     (38-token prompts, ~1030 tok/s) with twelve prefix-curve runs (up to
     2086 tokens, down to 492 tok/s). That pulled the 8-slot point down and
     flattened the slope from 9% to 2% per doubling. Prompt length is a
     WORKLOAD effect; pooling it with saturation destroyed both.

  3. A burstiness term in the queue model. It was added to explain a run that
     measured 1076 ms against a 1984 ms prediction - and THAT RUN WAS THE
     CONTAMINATED ONE. The clean rerun measures 1972 ms, which the plain
     full-wave model predicts to within 1%. Extra complexity had been fitted
     to an artifact. Removing it brought k from 7.95 to 0.99.

  All three were found by checking predictions against measurements that
  already existed. None would have been caught by a better fit.

WHAT THE PLANNER REFUSES TO DO
  - plan at all when the ledger audit fails (exit code 2): a confident wrong
    plan is worse than no plan
  - price a configuration the hardware cannot run (fp8 on compute 8.6)
  - treat a latency or accuracy limit as a penalty rather than a refusal
  - rank on cost alone when the gap is inside the noise floor
  - recommend concurrency above max-num-seqs (Finding #22)
  - present an extrapolated capacity without saying so
  - claim measured accuracy; the drop figures are labelled as placeholders
    until quality.py runs

FINDING #24 - THE PLANNER'S EXTRAPOLATION WAS 26% OPTIMISTIC, AND MEASURING
              IT CAUGHT THAT
Date: 2026-11-23 | Severity: CRITICAL | Status: Confirmed and corrected
================================================================================

THE TEST THAT WAS SET UP IN ADVANCE
  The planner's top recommendation rested on 64 slots, a configuration it had
  never seen. It flagged that as EXTRAPOLATED and predicted:

    predicted capacity : 47.7 req/s   (5977 tok/s, saturation 73%)

  Three outcomes were possible and all three were stated before the run:
  landing near 47 would validate one doubling of extrapolation; landing near
  the linear 64 would mean the planner was too pessimistic; landing well below
  47 would mean it was too OPTIMISTIC, which is the dangerous direction.

THE MEASUREMENT
    measured capacity  : 37.0 req/s   (4730 tok/s, saturation 58%)
    planner was        : +26% optimistic

  The dangerous outcome. A planner promising 47.7 req/s where 37.0 exists
  sends a deployment live under-provisioned by a quarter.

WHY THE LOG-LINEAR MODEL COULD NOT SEE IT
   slots    tok/s  ceiling  achieved  gain vs previous
       8   1014.6     1024       99%                 -
      16   1870.4     2049       91%             1.84x
      32   3466.7     4097       85%             1.85x
      64   4730.4     8195       58%             1.36x

  The doubling gains give it away: 1.84x, 1.85x, then 1.36x. Throughput is
  approaching a CEILING, not losing a fixed share per doubling. Three points
  spaced one doubling apart cannot distinguish "loses 9% each time" from
  "approaching a limit", and the two disagree violently once extrapolated.

THE CORRECTED MODEL
    throughput = t_max * slots / (slots + k)

  Fitted on all four points: t_max = 11,096 tokens/s, k = 78 slots (half the
  ceiling at 78 slots). Errors: 8 slots +0%, 16 +0%, 32 -6%, 64 +8%, against
  the log-linear model's +26% at 64.

  The structural point matters more than the accuracy: this form CANNOT
  exceed t_max however many slots are added, so it cannot promise capacity
  that does not exist. And t_max is the power cap of Finding #21 expressed
  in tokens per second.

  Compare the extrapolations:
     128 slots: hyperbolic  7185 tok/s   log-linear 10412 tok/s
     256 slots: hyperbolic  9006 tok/s   log-linear 17740 tok/s

  With 64 slots now measured, the planner predicts 39.1 req/s against 37.0
  measured: +5.7%, down from +26%.

TWO SAFEGUARDS ADDED
  1. Beyond the measured range a 15% haircut is applied to capacity, and the
     recommendation says so. The haircut is one-sided on purpose: being
     optimistic about capacity ships an under-provisioned deployment, while
     being pessimistic only understates a recommendation.
  2. A fit implying NO ceiling is refused outright, with the reason printed,
     rather than used.

A BUG THIS EXPOSED IN MY OWN FIT
  The grouping stored each run's SHARE of the slots/step ceiling, which is
  what the log-linear version needed. Feeding shares to a hyperbola inverts
  the slope, so the fit was refused for "implying no ceiling" - and the
  refusal message then printed a contradiction ("4 slot counts measured;
  needs 3"). The refusal was right for the wrong reason. Fixed to store raw
  throughput, and every refusal now prints why.

WHAT THIS EPISODE IS WORTH TO THE PAPER
  This is the project's own thesis applied to itself, with the prediction
  recorded BEFORE the measurement:
    - the planner made a specific, falsifiable claim
    - it labelled the claim as extrapolation rather than hiding it
    - the measurement refuted it by 26%, in the harmful direction
    - the refutation identified the structural error, not just the number
  A tuner that had simply reported "use 64 slots" would have been wrong and
  silent about it.

NEW BEST CONFIGURATION MEASURED
  b64_c64 : $0.0024/1K, p99 1805 ms (inside a 2 s SLO), 4730 tok/s
  b32_c32 : $0.0035/1K, p99 1217 ms, 3231 tok/s
  -> 31% cheaper with the SLO still met. Also b64_c32 measured 3245 tok/s,
     almost exactly b32_c32's 3231, which is min(slots, concurrency) holding
     once more (Finding #22).

FINDING #25 - QUALITY NEEDS SIX RUNS, NOT SIX HUNDRED
Date: 2026-11-23 | Severity: MEDIUM | Status: Built, not yet run on this model
================================================================================

WHY QUALITY IS CHEAP TO MEASURE
  Two properties of quantization, neither of them about the GPU:

  1. Output quality depends on how far the WEIGHTS were compressed, not on
     which chip runs them. The same INT4 checkpoint picks the same tokens on
     a laptop GPU and on an A100, so a measurement taken here transfers to
     other hardware.
  2. Quality does not depend on batch size, caching or concurrency. Those
     change WHEN a token is computed, not WHICH token is chosen.

  So a search space of hundreds of configurations needs one quality run per
  (model, quantization) pair. On this project that is six runs, not six
  hundred - and it is why the cost model can be fitted from throughput data
  that carries no quality information at all.

HOW IT IS SCORED
  Token log-probabilities from the server, with zero new tokens and echo on.
  No sampling is involved, so the measurement does not depend on temperature
  or on the model following an output format. Perplexity over a fixed
  passage, plus multiple choice scored by mean token log-probability so a
  longer choice is not penalised for its length.

THE HONEST LIMITATION, STATED IN THE OUTPUT
  The corpus is small and embedded in the script, so the absolute numbers are
  NOT comparable to published benchmarks. What is valid is the RELATIVE
  change against an fp16 baseline measured on the same text, which is exactly
  what the planner needs. The report says this rather than implying a
  benchmark, and it warns that with 8 questions one flipped answer moves
  accuracy by 12 percentage points.

WHAT CHANGED IN THE PLANNER
  The accuracy column was a table of plausible numbers. It now reads
  quality.py's store, and distinguishes the two cases out loud:
      accuracy : measured for fp16, awq (from quality.json)
      accuracy : NOT MEASURED - using fallback estimates. Run quality.py.
  A quantization with no measurement falls back to the table AND is reported
  as unmeasured. Mixing the two silently would let a guess decide a
  deployment, which is the failure mode this project is about.

ACTION ITEM
  Run it on this model: fp16 baseline first, then an AWQ checkpoint.

FINDING #27 - TWO QUALITY METRICS, SAME DATA, OPPOSITE VERDICTS
Date: 2026-11-23 | Severity: HIGH | Status: Measured
================================================================================

MEASURED (same 266-token corpus, same requests)
                     0.5B FP16     1.5B AWQ    change        verdict
  perplexity             53.16        36.18     -31.9%   large change
  top-1 accuracy         31.6%        32.3%     +0.8pp   nothing shown
                   CI 26-37%     CI 27-38%              intervals overlap

  Both numbers come out of the same server calls, so nothing about the setup
  differs between them.

THIS IS NOT A CONTRADICTION
  Perplexity reads the whole distribution: how confident the model was about
  what came next. Top-1 asks a narrower question: was its FIRST choice the
  right token.

  The larger model is far better calibrated on the tokens it already got
  right, which moves perplexity a great deal, while the SET of tokens it
  ranks first barely changes on this prose. Two different questions, two
  different answers, both correct.

THE PRACTICAL CONSEQUENCE: SENSITIVITY, NOT TRUTH
  Tokens needed for top-1 to resolve a given difference, at p = 0.32:
      5pp  ->  1,337 tokens   (5x the current corpus)
      2pp  ->  8,359 tokens   (31x)
      1pp  -> 33,437 tokens   (126x)

  At 266 tokens top-1 carries +/-5pp, so a real 3pp drop from quantization
  would pass unnoticed. Perplexity caught a 32% change on the very same 266
  tokens.

  So perplexity is the instrument for DETECTING a change, and top-1 is the
  one closer to what a user experiences. Keeping both is right; treating
  them as interchangeable is not.

WHAT THIS CHANGES IN THE LIBRARY
  Nothing in the code, and that is the point: quality.py already refused to
  record a drop from the overlapping top-1 intervals, and the planner already
  refused the whole comparison for being cross-model. Two independent guards
  both held on a result that looked, at a glance, like a 32% quality gain
  from four-bit weights.

  The lesson for the write-up is about instruments rather than about this
  model: a metric that shows no change may be reporting its own resolution
  rather than the world's behaviour, and the only way to tell is to compute
  what it COULD have detected.

ACTION ITEM
  1. Expand the corpus to ~1,500 tokens if top-1 is to be quoted at 5pp
     resolution; keep perplexity as the primary signal regardless.
  2. When reporting a null result anywhere in this project, state the
     smallest effect the measurement could have seen.

FINDING #28: THE CORPUS NOW RESOLVES 3.3pp, NOT 5pp - AND 5pp WAS THE WRONG
             NUMBER TO QUOTE IN THE FIRST PLACE
================================================================================
Date: 2026-11-23
Files: quality.py (PASSAGES 5 -> 27, 266 -> ~1520 tokens; new field
       top1_min_detectable_pp)

WHAT WAS DONE
  The embedded passage corpus was expanded from 5 passages (240 words, 266
  tokens) to 27 passages (1369 words, ~1520 tokens), all in the same domain
  (LLM serving, GPU memory, measurement) so the text stays comparable in
  difficulty to the original five.

WHAT THE ARITHMETIC ACTUALLY SAYS
  Finding #27 recorded "+-5pp" for the 266-token corpus and said ~1337 tokens
  would "resolve 5pp". Both numbers used the ONE-SAMPLE Wilson half-width.
  That is the wrong quantity for the question being asked. The question is
  always a COMPARISON of two configurations, and a difference of two
  independent proportions has roughly sqrt(2) times the standard error:

      mde = 1.96 * sqrt(2 * p * (1-p) / n)       (p ~ 0.32)

      n =  266 tokens  ->  7.9pp between two runs
      n = 1520 tokens  ->  3.3pp between two runs
      n = 3400 tokens  ->  2.2pp
      n = 9500 tokens  ->  1.3pp

  So the real resolution before this change was 7.9pp, not 5pp, and the
  expanded corpus buys 3.3pp, not 5pp. The target in #27 was understated by
  a factor of about 1.4 throughout.

CONSEQUENCE FOR THE QUANTIZATION QUESTION
  A 3pp accuracy drop from INT4 - the size usually reported in the
  quantization literature - sits just BELOW the 3.3pp this corpus can see.
  Top-1 accuracy at 1520 tokens therefore still cannot settle that question.
  Perplexity remains the primary quality signal: it reads the whole
  distribution at every position rather than a win/lose bit, and it separated
  the two models by 31.9% (finding #26) where top-1 differed by 0.7pp with
  overlapping intervals (finding #27).

WHAT CHANGED IN THE CODE
  quality.py now prints, next to every top-1 figure, the smallest difference
  two runs of that size could have detected, and stores it as
  top1_min_detectable_pp. This is finding #27's second action item made
  mechanical: a null result in this project cannot be reported without the
  resolution that produced it.

HONESTY NOTE
  This finding corrects my own earlier arithmetic, not the hardware's
  behaviour. The expansion was still worth doing - 7.9pp to 3.3pp is a real
  gain - but it does not reach the threshold #27 claimed it would, and the
  claim that it would was mine.

ACTION

     top-1 are both measured over 1520 tokens:

       python quality.py --label fp16_0p5b --set-baseline
       python serve.py Qwen/Qwen2.5-1.5B-Instruct-AWQ --quantization awq
       python quality.py --label awq_1p5b
     The old 266-token numbers are not comparable with the new ones; the

  Before running, the fit was asked for 128 slots and said 7185 tok/s
  (t_max 12061, k 87). Measured: 3647 tok/s. The fit was 97% optimistic,
  against the 26% of finding #24.

WITHDRAWN THE NEXT DAY - READ FINDING #31 FIRST
  The curve below is confounded. The 128-slot run was the last run of the
  11-23 session; the 64-slot run was from its middle. On 11-24 the SAME
  64-slot configuration was re-measured three times across 31 minutes and
  gave 3083, then (via 96 and 128 slot runs) 801 tok/s - a 6x spread on one
  configuration with 0.2% internal noise each time. Slot count and machine
  state moved together, and the reversal control in #31 shows machine state
  is the driver. The decline below is NOT a property of slot count. The
  fence added here is still correct - the planner must not promise capacity
  at slot counts it has not measured - but the reason given for it was
  wrong, and the peak at 64 is not established.

THE MEASURED CURVE
      slots      tok/s     gain vs previous
          8       1015              -
         16       1870           1.84x
         32       3467           1.85x
         64       4730           1.36x
        128       3647           0.77x   <-- DOWN

  Throughput is not saturating. It PEAKS at 64 slots and declines. The
  hyperbolic form T = t_max * s / (s + k) is monotonically increasing in s
  for any positive t_max and k, so no choice of parameters can express this.
  The model is not mis-tuned; it is the wrong shape beyond the peak - the
  same class of error as the log-linear model of finding #24 and the
  share-of-ceiling bug, both of which also looked like bad numbers and were
  bad forms.

A WRONG EXPLANATION I GAVE FIRST, AND THE CORRECTION
  On seeing the server log I claimed the cause was the KV cache:
      GPU KV cache size: 110,160 tokens
      Maximum concurrency for 2,048 tokens per request: 53.79x
  and asserted that 128 slots "do not exist on this card". That is wrong for
  this workload. vLLM's 53.79x figure assumes every request fills
  max_model_len. The benchmark sends 38 input + 128 output = ~166 tokens, so
  110,160 / 166 = ~663 such sequences fit. KV capacity was never the
  constraint. The cause of the decline is still unknown; candidates are
  per-step scheduler cost at 128 sequences, attention-kernel efficiency at
  small per-sequence lengths, and the power cap of finding #21. A roofline
  estimate rules out KV bandwidth: at 128 slots the KV read adds ~160 MB to
  a ~990 MB weight read, which predicts a ~9 ms step against the ~35 ms
  measured (128 / 3647 s). The gap is 4x and is not memory traffic.

THE SECOND BUG, WHICH IS WORSE THAN THE FIRST
  The planner, re-run with this measurement on disk, still reported:
      saturation       : fitted on 8, 16, 32, 64 slots
  and printed no caution at all.

  My first explanation was that Saturation.fit's workload-shape tuple had
  put the run in a group of its own and `max(groups, key=len)` had discarded
  it. That was speculation and it was wrong. The actual cause is cruder:

      planner.py  ->  load_runs(Path(args.ledger))      # ledger.jsonl only
      bench.py    ->  runs/<label>_<stamp>.json         # never opened

  runner.py writes the ledger; bench.py writes per-run JSON and a CSV row.
  This run was launched by hand through bench.py, so it never entered the
  ledger, and the planner reads nothing else. Fourteen JSON records were
  sitting in runs/ that no part of the library had ever opened. The run was
  not excluded by a subtle grouping rule - it was never seen.

  So the single measurement that contradicted the model could not reach the
  model, for reasons of plumbing rather than physics. Every re-fit would
  have left 7185 tok/s standing. A fit that can only read the runs produced
  by one of its own two entry points is not a fit; it is a filter.

  Noted for the paper: TWO of my explanations in this finding were wrong
  before the right one (the KV cache, then the shape tuple), and both were
  stated with more confidence than the evidence carried. The measurements
  corrected both. That is the argument for the library, not against it - but
  the argument only works if the wrong turns are written down.

THE FIX - FENCING, NOT CORRECTING
  1. Saturation now records `observed`: every slot count seen anywhere in the
     ledger, collected BEFORE shape grouping, so a run the fit cannot use can
     still constrain it.
  2. `_check_against_observations()` runs after every successful fit and finds
     the peak, detects a decline past it, lists slot counts measured but not
     fitted, and reports any fitted point the curve misses by over 15%. These
     print as CAUTION lines in the header.
  3. `throughput_tok_s()` stops using the curve past the measured peak. In
     order of preference it returns: the measurement at that slot count if
     one exists; otherwise the nearest measurement past the peak at or below
     that slot count; otherwise the peak itself. Standing the peak in at 128
     slots would have reported 4730 where 3647 was measured - 30% optimistic,
     and optimism is the direction that under-provisions a deployment. Past
     the last observation the last falling measurement is carried forward
     rather than the peak, because nothing has shown a recovery.
  3b. load_bench_runs() and load_all_runs() in costmodel.py read runs/*.json,
     so hand-run benchmarks reach the planner. They are given to the
     saturation analysis only, NOT to the cost model or the audit: bench.py
     records no server configuration, so the latency and prefill fits would
     be keying off absent fields and audit() would read the absences as
     drift. The header now says how many such runs were admitted and that
     they act as ceilings only.
  4. `is_extrapolated()` now considers observed slot counts too, not only
     fitted ones, so a measured-but-unfitted point no longer counts as
     unexplored territory.
  5. Candidates past the peak carry an explicit note that more slots buy
     nothing and cost latency.

WHAT THIS COSTS THE LIBRARY, HONESTLY
  The planner can no longer say anything useful about slot counts above the
  highest one measured. That is the correct amount to be able to say. The
  previous behaviour - a smooth curve with a 15% haircut - looked like
  knowledge and was, at 128 slots, a 97% error in the direction that
  under-provisions a deployment.

STANDING RULE ADDED
  Any configuration the planner has never seen measured is a candidate for
  measurement, not a recommendation; and any run that disagrees with the fit
  must be able to reach the fit. Both were violated here, by the same run.

ACTION

     recommendation exceeds 64 slots.
  2. Re-measure 128 slots through runner.py (not bench.py) so the run carries
     a full config and joins the shape group: this also tests fix 1.
  3. Measure 96 slots to locate the peak more precisely than "between 64 and

     it.
  4. Diagnose the decline with gpuwatch.py running during a 128-slot bench:

THE RECOVERY
    time      config      tok/s   TPOT p50   e2e p99    noise
    11-23 09:42  64 slots   4730      ~10 ms        -        -
    11-24 10:47  64 slots    801      73.2 ms   9609 ms    0.2%
    11-24 11:15  64 slots   4749      12.5 ms   1766 ms    1.4%

  Fifteen minutes idle, no reboot, no driver change, no configuration change:
  801 -> 4749 tok/s on the identical configuration, which is within 0.4% of
  the figure measured 25 hours earlier. The degradation of finding #31
  accumulates under sustained load and clears with rest.

  This is good news twice over. The machine is not broken, and a rested
  measurement of this configuration reproduces to under half a percent across
  a day - which is better than the 2.2% noise floor the planner assumes. The
  ledger is salvageable; it just needs to record whether a run was rested.

WHAT THE CLOCK DATA SHOWED, AND WHY IT KILLED THE THROTTLING STORY
  Busy-sample medians from the three gpuwatch CSVs:

    run        SM MHz    power    throughput    throttle mask
    s64           945   29.8 W      3083         0x24
    s96          1410   20.0 W      1051         0x24
    s128         1395   20.0 W      1213         0x24

  The FASTEST run ran at the LOWEST clock. 945 MHz produced 3083 tok/s while
  1410 MHz produced 1051. Throttling cannot explain a slowdown that happens
  at higher clocks, and the throttle mask was identical (0x24) in all three
  runs - a constant cannot explain a difference.

  Power draw settles it. A throttled GPU consumes its full permitted power
  and is held back by clocks; this GPU drew LESS power (20 W against 29.8 W)
  during the slow runs. It was not being restrained, it was being starved:
  idle, waiting for work. The bottleneck had moved off the GPU.

THE THROTTLE COUNTERS ARE NOISE ON THIS CARD
    nvidia-smi -q -d PERFORMANCE, at idle:
        SW Power Capping     : 73445 us
        SW Thermal Slowdown  : 73445 us      <-- identical, to the microsecond
  gpuwatch reported both as active in 201 of 209 samples across a 231-second
  run; the driver's own counters total 73 milliseconds for each. The two
  cannot both be right, and two distinct causes reporting byte-identical
  totals is the signature of one combined flag rather than two measurements.
  On this laptop GPU, 0x24 is asserted essentially whenever the card is under
  load and means only that it is not at its single-burst boost ceiling.

  CONSEQUENCE: Finding #21 ("power cap active in 21% of samples") compared
  two readings of a meaningless flag and should not be cited. gpuwatch.py
  must stop reporting sw_power_cap and sw_thermal_slowdown as throttling on
  this hardware, and should report the BUSY-SAMPLE CLOCK and the POWER DRAW
  instead - both of which carried the real signal here, and in the opposite
  direction to the flag.

WHERE THE BOTTLENECK ACTUALLY WENT - STATED AS A HYPOTHESIS, NOT A RESULT
  bench.py runs on the same laptop as the server. The evidence is consistent
  with the host side becoming the limit under sustained load: GPU idle at
  reduced power, correct clocks, TTFT rising 68 -> 258 ms and TPOT 12.5 ->
  73.2 ms, host RAM and swap clear, load average under 1.6. A host spin test
  taken immediately after recovery ran 8M integer operations in 0.64 s; the
  same test has NOT been taken while degraded, so the hypothesis is untested.

  SMALLEST EFFECT THE AVAILABLE DATA COULD HAVE DETECTED: none - there is no
  measurement of host speed in the degraded state at all. This is recorded as
  a hypothesis precisely so it is not later cited as a finding.

  To test it: reproduce the degradation (sustained load for ~30 minutes),
  then run the spin test before touching anything. If it has moved from
  0.64 s, the host is the answer. If it has not, the limit is inside the
  serving stack and the next place to look is the scheduler's per-step cost.

WHAT THIS MEANS FOR THE MEASUREMENT PROTOCOL
  1. A run is valid only if the machine was rested. "Rested" now has a
     number attached: ~15 minutes idle restored full throughput from the
     worst state observed.
  2. Back-to-back sweeps are the problem, not long sweeps as such. The
     11-23 knee sweep produced self-consistent results because each
     configuration was short; the 11-24 sequence degraded because three
     benchmarks of 1536-3072 requests ran within 31 minutes.
  3. The reference control of finding #31 is not optional. With it, the
     11-24 sequence would have been thrown out automatically at the 96-slot
     run instead of being mistaken for a slot-count law for a day.

STILL OPEN, AND NOW MEASURABLE
  The original question - what happens between 64 and 128 slots - has no
  answer yet. All three attempts were contaminated. It needs one slot count
  per rested session, or a reference control between them, and it is worth
  doing properly because the planner's ceiling depends on it.

ACTION
  1. Implement the reference control in runner.py (finding #31, consequence 2).
  2. Strip sw_power_cap and sw_thermal_slowdown from gpuwatch's throttle
     verdict on this hardware; report busy-sample clock and power draw.
  3. Re-measure 64 / 96 / 128 slots with 15 minutes rest between each, and
     a 64-slot reference immediately before and after every one of them.
  4. Reproduce the degradation deliberately and run the spin test while it
     is degraded, to settle the host hypothesis.

FINDING #34: THE PLANNER HAD NO LATENCY MODEL FOR BATCHING - IT PRICED 8 AND
             128 SLOTS AT THE SAME 1033 ms AND SAID "THE LOWER LATENCY
             DECIDED IT (1033 vs 1033 ms)"
================================================================================
Date: 2026-11-24
Files: planner.py (step-time correction in price(), honest tie-break message,
       search space extended to 96 and 128 slots)

HOW IT SURFACED
  Once finding #33 let 96 and 128 slots into the search space, the planner
  recommended 128 and printed this:

    #  configuration                     GPUs     $/1K  e2e ms  cap r/s
    1  fp16_half_b128_len2048_kvauto        1   0.0049    1033     47.7
    2  fp16_half_b96_len2048_kvauto         1   0.0049    1033     42.9
    3  fp16_half_b64_len2048_kvauto         1   0.0049    1033     35.8
    4  fp16_half_b32_len2048_kvauto         1   0.0049    1033     23.9

    tie-break : fp16_half_b96... costs within 0.0%, inside the 5.6% noise
                floor, so the lower latency decided it (1033 vs 1033 ms)

  Every configuration, identical latency. The measured p99 end-to-end from
  the controlled sweep two hours earlier:

        64 slots   1806 ms
        96 slots   2539 ms
       128 slots   3248 ms      -  80% more than 64

  So the planner was ranking configurations whose real latency differed by
  80% as indistinguishable, and because capacity-based costing gives every
  single-GPU configuration the same $/1K, the ranking fell through to
  capacity and picked the largest slot count available. At an offered rate of
  20 req/s, 32 slots (23.9 req/s capacity) is sufficient and roughly halves
  the p99. The planner recommended the worst of the adequate options.

  The tie-break sentence is the bug stating itself out loud: two numbers that
  are equal cannot have a lower one. A message written to explain a decision
  revealed that the decision had no basis.

THE CAUSE
  cm.predict() derives TPOT from the decode roofline: bytes of weights over
  memory bandwidth, times a measured correction. That quantity depends on the
  model and the card and NOT on how many requests share a decode step, so it
  returned 7.91 ms for 8 slots and 7.91 ms for 128. It is a per-step figure
  being used as a per-request figure, and those are the same thing only at a
  batch size of one.

THE FIX, WHICH NEEDED NO NEW MEASUREMENT
  A decode step serves every occupied slot at once, so a request's
  inter-token time IS the step time:

      step_ms = 1000 * slots / throughput_tok_s(slots)

  The saturating fit of findings #30/#33 already supplies throughput at a
  slot count; it had simply never been asked for the latency implication.
  Checked against today's controlled sweep:

      slots   predicted step   measured TPOT p50   error
         64        13.58 ms          13.60 ms      -0.2%
         96        18.97 ms          19.00 ms      -0.2%
        128        23.97 ms          24.00 ms      -0.1%

  and end to end, against measured p99:

      slots   predicted e2e   measured p99   error
         64        1767 ms        1806 ms     -2.2%
         96        2457 ms        2539 ms     -3.2%
        128        3098 ms        3248 ms     -4.6%

FINDING #37: THE REAL MAPE IS 14%, NOT 9% - AND THE 9% HELD BECAUSE THE MODEL
             WAS NEVER TESTED WHERE IT WAS WRONG
================================================================================
Date: 2026-11-24
Files: costmodel.py (decode_step, fit_power_law, controlled-only fit and LOO,
       short-prompt filter, _step_for)
       planner.py (its own copy of the correction removed)

THE NUMBERS, BEFORE AND AFTER
                        before   after the control   target
      TPOT MAPE           9.0%        14.0%            15%
      TTFT MAPE          11.8%        21.5%            15%
      E2E  MAPE          10.0%        14.1%            15%
      cost MAPE          11.5%        15.1%            15%

  The 9-12% figures were cross-validated on a ledger with no reference
  control, few high-slot configurations, and runs taken in machine states
  nobody recorded. They were not wrong arithmetic; they were the right
  arithmetic on the wrong population. TPOT and E2E now sit inside target,
  TTFT and cost just outside, and all four are honest.

HOW THE FLAT TPOT SURVIVED SO LONG
  The first run of the recomputed validation showed its hand immediately:

      config                                   actual    pred     err
      fp16_half_b128_c128_len2048_u0.7_kvauto    2972    1113   -62.6%
      fp16_half_b96_c96_len2048_u0.7_kvauto      2319    1113   -52.0%
      fp16_half_b64_c64_len2048_u0.7_kvauto      1641    1113   -32.2%

  Three configurations, one prediction. Finding #34 had already found this in
  the planner and fixed it THERE - in a layer with no validation - leaving
  the cost model, which is the thing leave-one-out actually scores, still
  flat. The planner was better than its own cost model, which is an
  architecture smell: the correct law was living where nothing could grade it.

  It survived earlier because the search space stopped at 64 slots and the
  ledger had almost no high-batch runs. A model is not falsified by being
  fitted better; it is falsified by being asked a question it can fail.
  That is now three times in this project (#24, the share-of-ceiling
  inversion, and this).

THE LAW, AND WHERE IT HAD TO BE FITTED
      step_ms = c0 + c1 * batch^alpha,  batch = min(concurrency, max_num_seqs)
      measured: c0 7.50 ms, c1 0.0169, alpha 1.42, MAPE 2.1%, batches 4-128

  Three things had to be right before that 2.1% appeared, and each was wrong
  first:

  1. The batch is min(concurrency, slots), not slots. b16_c8 stepped in
     7.96 ms and b8_c8 in 7.89, while b16_c16 took 8.55. The slot limit is a
     cap; the concurrency is the load.
  2. Fitted on short prompts only. With chunked prefill on, prefill chunks
     interleave with decode steps, so a long prompt inflates TPOT: at a batch
     of 8 it ranges from 7.9 ms on 38-token prompts to about 17.7 ms on the
     2048-token prefix runs. Fitting across that drove alpha to the 2.0
     search boundary and held MAPE at 15.1% - one parameter carrying two
     effects.
  3. The filter had to be the PROMPT, not the full-price tokens. A cache hit
     makes full_price_tokens 38 while the prompt is still 2086 long, and
     chunked prefill works on the actual prompt either way. Filtering on
     full_price let every cache-hit prefix run back in and held the fit at
     12.0% with alpha bent to 1.87.

  c0 = 7.50 ms lands within 2% of the roofline step times the measured
  correction (5.15 x 1.46), which is what it should be: the weights are read
  once per step whatever the batch, and everything above that floor is
  per-sequence work. The intercept was not fitted to match the roofline; it
  agreed with it, which is the only kind of confirmation worth anything here.

AND THE FIT ITSELF IS NOW CONTROLLED
  CostModel.fit and validate both prefer reference-controlled runs when at
  least eight exist, exactly as the saturation fit does. The evidence for
  that rule is alpha: fitted across mixed machine states it came out at 1.87,
  and on controlled runs alone 1.42. alpha is a physical exponent - how
  per-sequence attention cost grows - and it had bent by a quarter to absorb
  platform drift. A coefficient that moves when the laptop's mood changes is
  not measuring the hardware.

THE GAP THAT REMAINS, STATED PLAINLY
  TTFT at 21.5% is the weakest prediction, and the worst rows are the
  long-prompt ones (sp2048 at -42%, sp128 at +24%). The cause is known and
  unmodelled: chunked prefill couples prefill and decode, so prompt length
  changes inter-token latency and prompt length interacts with the batch.
  The term is not guessed at here because the TPOT values for those runs have
  not been extracted; writing a plausible formula without them would be
  fitting a story.

  SMALLEST EFFECT THE CURRENT DATA COULD DETECT on that term: unknown, for
  the same reason. It is recorded as an open measurement, not a result.

ACTION
  1. Extract ttft_p50 and tpot_p50 for the prefix runs and fit the chunked
     prefill term.
  2. Re-run the baseline, quant and kvcache sweeps with --reference-every so
     those coefficients are controlled too.

FINDING #38: AN UNMEASURED CONFIGURATION LOOKED CHEAPEST *BECAUSE* IT WAS
             UNMEASURED - THE WORST FAILURE THIS PLANNER CAN HAVE
================================================================================
Date: 2026-11-24
Files: costmodel.py (_step_for with fallback, "borrowed" flag)
       planner.py (borrowed configurations rank below measured ones, clean
       message for a missing ledger, VERIFY IT prints the user's own command)
       pkg/ (pyproject.toml, cli.py, sync.py, tests/test_smoke.py)

WHAT HAPPENED
  Installed as a package and run for the first time, the planner recommended:

      fp16_bfloat16_b128_len2048_kvauto   1 GPU   $0.0049   1123 ms   47.5 r/s

  Every bfloat16 row showed the same 1123 ms, while the measured half rows
  showed 1209 ms and up. bfloat16 has never been measured in this project.

  Cause: the batch law is keyed on (model, quantization, dtype). With no
  bfloat16 entry the lookup missed, the code fell back to the flat per-step
  figure, and the flat figure is LOWER than the batch-aware one at every
  batch above about 16. So the configuration with no measurements behind it
  got the most optimistic latency in the table, and won.

  The planner's own cross-check caught it and said so:

      the saturation fit implies a 21.0 ms decode step at 128 slots while the
      cost model predicts 8.6 ms (144% apart)

  That note exists because of finding #35, which demoted the planner's
  unvalidated copy of the law to a cross-check rather than deleting it. The
  check fired on its first real outing, on a bug introduced after it was
  written. Keeping a disagreeing second estimate around - clearly labelled
  as not authoritative - paid for itself within the hour.

WHY THIS CLASS OF BUG IS THE WORST ONE HERE
  A planner that is 20% wrong about a measured configuration costs money. A
  planner that systematically prefers configurations it knows nothing about
  is actively anti-correlated with its own purpose: the less evidence a
  choice has, the better it scores. Every other refusal in this library
  (extrapolation haircuts, the audit, the reference control) exists to stop
  confidence outrunning evidence, and this one quietly inverted it.

THE FIX
  1. The batch law now falls back across dtype and quantization within the
     same model, because how a step grows with the batch is a property of the
     batch - KV reads and attention - and not of the number format. The
     fallback says in a note that it is borrowing.
  2. predict() returns a "borrowed" flag. The planner reads the flag, not the
     note: a ranking decision must not depend on matching English.
  3. A borrowed configuration is marked extrapolated, so it ranks BELOW any
     measured configuration even when it prices lower.

  After the fix the pick is fp16_half_b32 at 1209 ms, latency differs per
  slot count (983 / 1044 / 1209 / 1662 ms), and at a 2000 ms p99 the 96- and
  128-slot configurations are correctly refused as infeasible rather than
  recommended.

TWO PACKAGING BUGS, SAME ROOT CAUSE: NOTHING LOOKED
  1. planner.py imports costmodel in THREE places - once at module level and
     twice inside functions. Only the module-level one was made relative. The
     package imported fine and `inferplan plan` died on the first real call.
     A test that imports a module proves nothing about imports that happen
     when it runs.
  2. pyproject.toml declared no dependencies, with a comment explaining
     proudly that none were needed. bench.py imports aiohttp. The wheel
     installed cleanly into a fresh virtual environment and failed the moment
     a command touched the benchmark.

  Both came from hand-copying files into the package. sync.py now does it and
  reported "planner (3 rewrite(s))" the first time it ran - the count I had
  got wrong by hand. tests/test_smoke.py walks the AST of every module for
  flat sibling imports at any nesting depth, parses pyproject.toml to check
  every third-party import is declared, and EXECUTES every command's --help
  so a deferred import cannot hide. Both bugs fail those tests.

ALSO FIXED, SMALLER
  A missing ledger raised a FileNotFoundError traceback. That is the normal
  state the first time anyone runs the tool, so it now gets one sentence and
  the command to run instead. The first impression a tool makes is the error
  it shows someone who has not done anything wrong yet.

  VERIFY IT printed "python runner.py ...", which an installed user does not
  have. It now prints "inferplan sweep ..." when running as a package. A
  verification step the reader cannot paste is advice they will skip.

FINDING #39: WHAT LENGTHENS THE DECODE STEP IS THE CONTEXT, NOT THE PREFILL -
             AND I ASSERTED THE OPPOSITE TWICE, FROM MISREAD COLUMNS
================================================================================
Date: 2026-11-24
Files: costmodel.py (decode_prompt, fit_two_term, paired check,
       --explain-decode)

WITHDRAWN THE SAME DAY - THE DATA WAS CORRUPT. READ FINDING #40.
  The cached/uncached pairs below are not pairs. runner.py matched each run
  to its metrics with a prefix glob, so every prefix-caching-ON run in the
  11-24 sweeps recorded ANOTHER configuration's numbers - usually its own
  _nopc sibling from 11-20. The "cached" and "uncached" rows at each context
  were therefore, in several cases, literally the same measurement, which is
  why they agreed to 0.04 ms.

  results.csv was correct the whole time. In it, sp2048 reads 8.44 ms cached
  against 14.45 ms uncached: the 6 ms gap I had claimed, and then talked
  myself out of. The conclusion below - that the full-price term is zero -
  is wrong, and the two-term model of finding #37 stands.

  What I got right in this finding was the method: look at the inputs rather
  than argue about the outputs. I just did not look far enough back, and
  stopped at the ledger instead of the file the ledger was built from.

THE RESULT
  TPOT, measured at batch 8 across five shared-prefix lengths with prefix
  caching on and off:

      context    cached    uncached    gap      gap as % of step
          166      7.99        8.02   +0.03            0.4%
          294      8.54        8.53   -0.01            0.1%
          550      9.59        9.57   -0.02            0.2%
         1062     11.49       11.56   +0.07            0.6%
         2086     14.41       14.45   +0.04            0.3%

  Cached and uncached runs at the same context step at the same rate, to
  within a few hundredths of a millisecond on steps of 8 to 14 ms. Whether
  the cache served the prompt or the GPU computed it makes no measurable
  difference to inter-token latency.

  What does change it is the context itself: 38 tokens of context gives a
  7.25 ms step and 2086 gives 14.41 ms, which is 0.0035 ms per token. The
  fitted coefficient came out at 0.00350. Decode attends over the whole
  sequence, so a longer sequence costs more per token - and a cache hit
  does not shorten the sequence, it only avoids computing it once.

      TPOT = 7.24 + 0.0135 * batch^1.45 + 0.0035 * (context - 38)

  With that, TPOT predicts to 8.1% MAPE under leave-one-out, E2E to 9.5% and
  cost to 11.0% - three of four metrics inside target for the first time in
  this project.

HOW I GOT IT BACKWARDS, TWICE
  I claimed, in two separate messages and with a confident physical story
  attached, that chunked prefill inflates TPOT and that sp2048 measured
  8.44 ms cached against 14.45 ms uncached - a 6 ms gap I attributed to
  prefill chunks stealing decode steps.

  There is no such gap. The numbers came from an awk command whose column
  indices were wrong: results.csv has a stale header (see below), so the
  field I read as tpot_p50 was a different percentile of a different metric.
  I then fitted a two-term model to those numbers offline, got a clean 1.3%
  MAPE, and used that agreement as evidence the story was right. A good fit
  to the wrong column is not evidence of anything.

  When the ledger's own fit disagreed with my offline one - putting 0.00002
  on full-price where I had 0.00305 - I concluded the ledger fit was wrong,
  because the measured 6 ms gap "had to come from somewhere". The gap was
  the thing that did not exist.

  What settled it was looking at the inputs instead of arguing about the
  outputs: --explain-decode prints batch, full-price tokens, context,
  predicted and measured step for every run, and the cached/uncached pairs
  sat on top of each other immediately.

THE CHECK THAT FIRED, AND THE SECOND MISTAKE INSIDE IT
  The paired check was written specifically to catch a wrong split between
  the two prompt terms, and it did fire - but it reported:

      PAIRED CHECK FAILED on 3/5 prefix length(s): sp128: measured gap
      0.03 ms, model says 0.00 ms

  A 30% relative test applied to a 0.03 ms gap is meaningless; the gap is
  noise. The check was calling a thing it could not resolve a disagreement,
  which is a different claim and the more alarming one. It now has three
  outcomes instead of two:

      DISAGREES      - gap is resolvable and the model misses it
      unresolvable   - gap is below 2% of the step; says nothing
      passed         - resolvable and reproduced

  And when every pair is unresolvable, the full-price coefficient is set to
  ZERO rather than kept at its fitted 0.00002. A number the data cannot see
  should not be carried, because someone - quite possibly me in two weeks -
  will quote it as a measurement.

  SMALLEST EFFECT THIS COULD HAVE DETECTED: a gap of about 2% of the step,
  so roughly 0.16 ms at batch 8. If chunked prefill costs less than that per
  step, this experiment cannot see it, and nothing here rules out a small
  effect. It rules out the 6 ms one I claimed.

A DATA-INTEGRITY BUG WORTH ITS OWN LINE
  results.csv has a header from an older version of bench.py, written before
  shared_prefix_tokens was added as a column. bench.py writes the header only
  when the file does not exist, so adding a column left the header one field
  short of every subsequent data row. Anything reading that file by column
  name or index gets a different metric than it asked for, silently. This is
  what produced both of my wrong claims above, and it is still unfixed.

ACTION
  1. Fix bench.py: on append, compare the existing header with the expected
     columns and refuse - or rotate the file - rather than appending rows
     that do not match it.
  2. The remaining 19.7% is TTFT, not TPOT. Its worst rows are the long

     (0.0488 ms/token, fitted on 5 runs) is the next thing to look at.
  3. When a fit disagrees with an expectation, read the inputs before

FINDING #40: A PREFIX GLOB PAIRED RUNS WITH OTHER RUNS' MEASUREMENTS, AND

Date: 2026-11-24

THE BUG, IN ONE LINE
    files = sorted(d.glob(f"{cfg.label()}_*.json"))     # runner.run_bench

  Every label in this project is a prefix of longer ones.
  "fp16_half_b8_c8_len4096_u0.7_kvauto" is a prefix of that label plus

    OLD pattern picked : ..._kvauto_sp512_nopc_20261120T080427Z.json
    NEW pattern picked : ..._kvauto_20261124T090536Z.json

WHAT IT CORRUPTED

  already had a JSON on disk recorded a different run's metrics:

    11-24 run       ledger said   that number belongs to
    sp0    pc          1267.47    11-20's sp512_nopc
    sp128  pc           900.79    11-20's sp128_nopc
    sp256  pc           977.81    11-20's sp256_nopc
    sp512  pc          1267.47    11-20's sp512_nopc
    sp1024 pc          1223.28    11-20's sp1024_nopc
    sp2048 pc          1979.76    11-20's sp2048_nopc

  The 11-20 sweep escaped it by accident: it ran the configurations in label
  order, so when sp0 ran at 07:43 the longer-suffix files did not exist yet.
  The bug needed a SECOND run of the same sweep to show itself, which is why
  it survived four days.

WHY IT WAS INVISIBLE
  bench.py printed the right numbers live, and wrote the right numbers to
  results.csv and to runs/*.json. Only the ledger - the file the cost model
  learns from - got the wrong association. So every sweep looked perfect on
  screen, every CSV row was correct, and the model was quietly being fitted
  on mismatched pairs.

  It surfaced as a two-line oddity in a diagnostic table: two different
  configurations showing an identical 1267 ms, and one of them a value that
  did not match what the same run had printed. The honest check that caught
  it was comparing the ledger against results.csv - two records of the same
  measurement that should have agreed.

WHAT IT INVALIDATED, AND WHAT IT DID NOT
  INVALIDATED:
    - Finding #39 entirely. Its paired check compared, in several cases, one
      measurement with itself. Withdrawn; see the note at its head.
    - The cost model's prefill stage-2 coefficient (0.0488 ms per cached
      token), which produced the visible nonsense "1000 tokens: 47 ms at
      full price vs 49 ms cached" - cached tokens cannot cost more than
      computed ones.
    - TTFT's 19.7% MAPE, and the prompt term of the decode fit.
  NOT INVALIDATED:
    - Findings #19 and #36's prefix-caching tables. Both were read from the
      sweeps' live output, not the ledger.
    - The knee law (#22, #36), the saturation fit (#33) and the reference
      control results (#31-#35): those labels have no longer siblings, apart
      from one b8_c8_len2048 run.
    - results.csv and runs/*.json, which were always right.

THE FIX, AND WHY NO RE-MEASUREMENT IS NEEDED
  run_bench now accepts only "<label>_<YYYYmmddTHHMMSSZ>.json", matched by
  regex rather than by prefix glob.

  And because the JSON files were never wrong, the ledger is repairable
  rather than lost: repairledger.py re-pairs each row with the file whose
  name matches its label exactly and whose stamp is nearest that row's
  timestamp, backs up the original, and rewrites the metrics. Nineteen
  minutes of sweeping does not have to be repeated to undo a glob.

      inferplan repair            # report what would change
      inferplan repair --write    # apply, with a backup
      inferplan fit               # re-learn from the repaired ledger

THE LESSON THAT GENERALISES
  Three records of the same measurement existed - the live output,
  results.csv, and the ledger - and they disagreed for four days without
  anyone noticing, because nothing compared them. Redundant records are only
  a safeguard if something reads both. This is the same shape as finding
  #30's unread runs/ directory and finding #38's unverified dependency list:
  the data to catch the error was already on disk each time.

  Also: the paired check of finding #39 is correct code that gave a wrong
  answer because its inputs were wrong. Once the ledger is repaired it will
  see 6 ms gaps, resolve them, and keep both prompt terms by itself - no
  change needed. A guard that reads the data cannot be better than the data,
  and that is an argument for fixing data pipelines rather than adding more
  guards downstream of them.

ACTION
  1. inferplan repair --write, then inferplan fit. Expect the prefill
     stage-2 nonsense to disappear and TTFT to move.
  2. Re-check whether the full-price decode term returns with resolvable
     gaps, as it should.
  3. Add a check that compares the ledger with results.csv row by row, since
     that comparison is what found this.

FINDING #41: COMPLETIONS STOP SHORT OF max_tokens - BUT FEEDING THE MEAN INTO
             A PERCENTILE MADE THE PREDICTIONS WORSE, NOT BETTER
================================================================================
Date: 2026-11-24
Files: bench.py (out_tokens_mean, out_tokens_p50 recorded)
       costmodel.py (separate statistics for latency and for cost)
       repairledger.py (recovers the mean from per-pass counts)

WHAT WAS MEASURED
  Every run's mean completion length, recovered from the per-pass token
  counts already on disk:

      len2048 runs (knee, slots, reference)   exactly 116.0 tokens
      prefix runs (len4096, sp128..sp2048)    95.7 to 110.8 tokens
      max_tokens                              128

  So the cost model, which assumed 128, was over-estimating the work in
  every single run by 9 to 25%. And because the queue term is proportional
  to the output length, that inflated TTFT as well as E2E - which is why
  TTFT was the last metric over target and why every large error in the
  worst-five list was an OVER-prediction.

  That part of the hypothesis was right.

WHAT HAPPENED WHEN I USED IT
      metric          given the mean      assuming max_tokens
      TPOT                   2.3 %                   -
      TTFT                  18.2 %                17.2 %
      E2E latency           10.5 %                 5.5 %
      cost per 1K            7.8 %                 8.2 %

  Latency got WORSE and cost got BETTER. Every large error flipped from
  over-prediction to under-prediction (-23%, -17.5%, -14.6%).

  The cause is a statistics error of mine, and the split in that table is
  the proof of it. e2e_p50 is the latency of the MEDIAN request, and I was
  predicting it from the MEAN length. When most requests run to the
  max_tokens limit, the median request is AT the limit while the mean is
  dragged below it by the minority that stop early - so 128 was the right
  number for the percentile all along, and 116 was a known-wrong statistic
  applied with confidence.

  Cost improved in the same change because cost IS total work divided by
  requests, where the mean is the correct statistic. One substitution made
  one metric better and another worse, in exactly the pattern that mixing a
  mean with a percentile produces. The data diagnosed it in a single run.

THE FIX
  Two lengths, used where each belongs:
      latency (e2e, ttft)   -> the MEDIAN completion length
      cost, throughput      -> the MEAN completion length
  bench.py now records both. When the median is unknown the fallback is
  max_tokens, NOT the mean: the limit is an upper bound that happens to be
  close, while the mean is wrong in a direction that looks like skill.

  The existing JSON files hold only per-pass totals, so the mean could be
  recovered for all 49 rows without re-measuring, but the median cannot. It
  will appear from the next sweep onward, and the left column of the
  validation table is the one to watch when it does.

WHAT THIS SAYS ABOUT THE TWO-COLUMN REPORT
  The report was added in the same hour to separate "the latency model is
  wrong" from "the length assumption is wrong". It immediately showed that
  the latency model was fine and my new input was wrong - the opposite of
  what I built it expecting to see. A diagnostic that can only confirm you
  is not a diagnostic.

HONEST STATE OF THE FOUR METRICS
  TPOT 2.3%, E2E 5.5%, cost 8.2% against a 5.6% noise floor, all under the
  15% target; TTFT 17.2% and still over. TTFT's remaining error is not the
  output length - that has now been tested both ways - and the next thing to
  look at is the queue term, which is fitted on three oversubscribed runs.

  SMALLEST EFFECT THESE NUMBERS CAN RESOLVE: the noise floor is 5.6%, so
  TPOT at 2.3% and E2E at 5.5% are at or below the point where model error
  and measurement error are indistinguishable. They should not be quoted as
  better than the instrument.

FINDING #42: THE MEDIAN LENGTH FIXED E2E AS PREDICTED AND DID NOT FIX TTFT AS
             PREDICTED - TTFT'S 16.5% IS A 4 ms MISS ON A 27 ms QUANTITY
================================================================================
Date: 2026-11-25
Files: costmodel.py (absolute error reported alongside MAPE)
Runs:  prefix (6.4 min, reference spread 0.2%) and prefix_curve (11.5 min,
       spread 0.9%), both re-run so bench.py could record out_tokens_p50

THE PRE-REGISTERED PREDICTION, SCORED
  Written before the sweeps ran:

    (a) "sp1024 rows will move from +21%/+20% to within +-5%"
        -> they left the worst-five entirely; the largest error anywhere is
           now +8.5%. Close enough to count, slightly optimistic.
    (b) "other rows will not move by more than 2%"
        -> WRONG. sp2048 and b128_c128 both moved by more than that and are
           now the worst rows at +7.4% and +5.9%.
    (c) "TTFT MAPE will fall below 10%"
        -> WRONG. It went 17.2% -> 16.5%.

  One of three right. Recorded in full because a prediction that is only
  reported when it lands is not a prediction.

WHAT DID IMPROVE
      metric       before   after    with max_tokens only
      TPOT           2.3%    3.2%           -
      E2E            5.5%    3.0%         5.4%
      cost           8.2%    8.0%         7.7%
      TTFT          17.2%   16.5%        16.5%

  E2E at 3.0% against a 5.6% noise floor: the latency model is now closer to
  the measurements than the measurements are to each other. The median/mean
  split of finding #41 is what did it - the left and right columns differ by
  3.0% against 5.4%, which is the length knowledge paying for itself.

  Also worth noting: the cached-token cost settled at 0.0006 ms, so a
  1000-token cached prefix now costs 1 ms against 46 ms computed - a 71x
  saving, up from the 28x of the previous fit and physically sensible for
  the first time in this project.

WHY (c) WAS WRONG, AND WHY IT WAS NEVER GOING TO BE RIGHT
  TTFT depends on the output length only through the queue term, and these
  runs have concurrency == max_num_seqs, so there is no queueing at all. I
  should have seen that before predicting the length would fix it.

  The real explanation is arithmetic, not physics. TTFT on this workload is
  25-32 ms. The model's median miss is about 4 ms. Four milliseconds is
  below any plausible scheduling jitter - it is roughly one decode step -
  and on a 27 ms quantity it reads as 16%. The same 4 ms on E2E's ~1000 ms
  would read as 0.4% and nobody would mention it.

  So TTFT's "OVER TARGET" was mostly a statement about TTFT's magnitude. A
  15% target applied uniformly to quantities spanning 27 ms to 3000 ms is
  not one target, it is four different ones.

THE FIX IS TO THE REPORT, NOT THE MODEL
  validate() now reports, next to every MAPE, the median absolute miss and
  the typical magnitude of the thing being predicted:

      TTFT  16.5%   median miss 4.2 ms on a typical 27.3 ms
      E2E    3.0%   median miss 31 ms on a typical 1030 ms

  Both lines describe the same model. The first invites a rewrite; the
  second says the rewrite would be chasing jitter. A percentage without a
  magnitude is a verdict without evidence, and this project has now been
  misled by one twice - here, and by the "+-5pp" of finding #28.

STATE OF THE MODEL ON THIS MACHINE, FINAL FOR THIS HARDWARE
  TPOT 3.2%, E2E 3.0%, cost 8.0%, TTFT 16.5% (4 ms). Noise floor 5.6%.
  Three of four are at or below the instrument's own repeatability, and the
  fourth is a few milliseconds. There is nothing further to learn about the
  model here that this GPU can teach; the next measurements have to come
  from different hardware.

ACTION
  1. Nothing further on this machine. The open questions are a data-centre
     GPU (does the FORM transfer, with coefficients refitted?) and the
     same-checkpoint INT4 comparison, which needs memory this card does not
     have.
  2. When reporting any percentage error in the writeup, give the absolute
     magnitude beside it.
